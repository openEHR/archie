# Archie: openEHR Library

Archie is a Java library for building openEHR tools and systems. See https://www.openehr.org for information about openEHR.

It supports the most recent versions of openEHR, including ADL 2, and contains:

- an ADL 2 parser and an Archetype Object Model (AOM) implementation
- archetype validation, flattening, operational template creation and diffing
- conversion of ADL 1.4 archetypes to ADL 2
- an implementation of the openEHR Reference Model (RM) 1.1.0, without the task planning part
- tools to create, query and validate reference model objects
- BMM and ODIN implementations
- JSON (Jackson 2 and Jackson 3), XML and ADL serialization

The ADL grammar is based on the ANTLR grammar written by Thomas Beale at https://github.com/openehr/adl-antlr.

Archie is licensed under the Apache license.

## Getting started

Archie requires Java 17 or higher.

### Adding Archie to your project

The easiest way to get started is to depend on `archie-all`, which contains everything: the AOM, the ADL parser, all tools and the openEHR reference model implementation.

Gradle:

```gradle
dependencies {
    implementation 'com.nedap.healthcare.archie:archie-all:4.0.0'
}
```

Maven:

```xml
<dependency>
    <groupId>com.nedap.healthcare.archie</groupId>
    <artifactId>archie-all</artifactId>
    <version>4.0.0</version>
</dependency>
```

If you want to work with the AOM and BMM without the openEHR reference model implementation, depend on `com.nedap.healthcare.archie:tools:4.0.0` and `com.nedap.healthcare.archie:referencemodels:4.0.0` instead.

### Modules

All modules are published under the group id `com.nedap.healthcare.archie`.

| Module | Contents |
|---|---|
| `archie-all` | Everything below, in a single dependency |
| `base` | Base classes, such as `Interval` and the parser error classes |
| `aom` | The Archetype Object Model, plus the ADL 2 and ADL 1.4 parsers and the ADL serializer |
| `tools` | Archetype validation, flattening, operational templates, diffing, ADL 1.4 conversion, RM object validation and creation, rule evaluation |
| `openehr-rm` | The openEHR reference model implementation |
| `referencemodels` | Built-in reference model metadata (BMM files and AOM profiles) |
| `bmm` | The BMM and P_BMM implementation |
| `odin` | ODIN parsing and serialization |
| `path-queries` | APath queries on reference model objects |
| `archie-utils` | Preconfigured Jackson and JAXB setup for archetypes and the openEHR reference model |
| `json-schema-tools` | Generates and validates openEHR JSON schemas from BMM models |
| `openehr-terminology` | A basic binding of the openEHR terminology |
| `i18n` | Translations of the messages generated by Archie |
| `grammars` | The ANTLR grammars for ADL, ODIN and XPath |
| `utils` | Basic utilities used throughout Archie |

### Quick start

A typical flow parses a set of ADL 2 archetypes, validates and compiles them in a repository, creates an operational template and uses it to validate a reference model object:

```java
MetaModelProvider metaModelProvider = BuiltinReferenceModels.getMetaModelProvider();

// 1. Parse your archetypes
ADLParser parser = new ADLParser();
InMemoryFullArchetypeRepository repository = new InMemoryFullArchetypeRepository();
for (Path file : adlFiles) {
    try (InputStream stream = Files.newInputStream(file)) {
        repository.addArchetype(parser.parse(stream));
    }
}

// 2. Validate and flatten all archetypes
repository.compile(metaModelProvider);
for (ValidationResult result : repository.getAllValidationResults()) {
    if (!result.passes()) {
        // handle result.getErrors()
    }
}

// 3. Create an operational template
Archetype archetype = repository.getArchetype("openEHR-EHR-OBSERVATION.blood_pressure.v1");
OperationalTemplate template = (OperationalTemplate) new Flattener(repository, metaModelProvider)
        .createOperationalTemplate(true)
        .flatten(archetype);

// 4. Validate reference model data against it
Observation observation = JacksonUtil.getObjectMapper().readValue(json, Observation.class);
RMObjectValidator validator = new RMObjectValidator(ArchieRMInfoLookup.getInstance(), repository,
        new ValidationConfiguration.Builder().build());
List<RMObjectValidationMessage> messages = validator.validate(template, observation);
```

The rest of this document describes each of these steps in more detail.

## Archetypes

Archetypes are the basis of openEHR. Archie can parse, validate, flatten, diff and serialize them.

### Parsing archetypes

```java
ADLParser parser = new ADLParser();
try {
    Archetype archetype = parser.parse(adlFile);
} catch (ADLParseException e) {
    e.getErrors().logToLogger();
    Archetype partial = e.getArchetype(); // a best effort partial result, may be null
}
```

The parser throws an `ADLParseException` when the ADL contains errors. The parser tries to continue after an error, so the exception contains all errors found, plus a partially parsed archetype when possible. This is useful for modeling tools that want to show as much as possible of an archetype with errors. By default, the parser also logs the errors. Call `parser.setLogEnabled(false)` to disable that.

### Archetype path queries

```java
AOMPathQuery query = new AOMPathQuery("/context[id1]/items[id2]/value");
ArchetypeModelObject object = query.find(archetype.getDefinition());

ArchetypeModelObject sameObject = archetype.getDefinition().itemAtPath("/context[id1]/items[id2]/value");

CAttribute attribute = archetype.getDefinition()
    .getAttribute("context").getChild("id1").getAttribute("items");
```

Path segments must use node ids, or a one-based index such as `items[2]`. Matching a segment on the
meaning of a node, as in `/context[systolic]/items`, is no longer supported. If you need to find a node
by its term text, compare the meaning yourself:

```java
CObject systolic = archetype.getDefinition()
    .getAttribute("context").getChildren().stream()
    .filter(child -> "systolic".equalsIgnoreCase(child.getMeaning()))
    .findFirst().orElse(null);
```

### Archetype repositories and validation

Archetypes are often related to other archetypes: they specialize a parent archetype, or include other archetypes. To work with a set of related archetypes, add them to an archetype repository and compile it:

```java
InMemoryFullArchetypeRepository repository = new InMemoryFullArchetypeRepository();
for (Archetype archetype : allArchetypes) {
    repository.addArchetype(archetype);
}
repository.compile(BuiltinReferenceModels.getMetaModelProvider());

for (ValidationResult result : repository.getAllValidationResults()) {
    // your code here
}
```

Compiling validates all archetypes. Each `ValidationResult` lists the errors and warnings for the archetype and contains the source archetype. If validation got far enough, it also contains the flattened archetype. Flattened archetypes are also available through `repository.getFlattenedArchetype(archetypeId)`.

`BuiltinReferenceModels.getMetaModelProvider()` provides the reference model metadata that is needed to validate and flatten archetypes. See [Reference model metadata](#reference-model-metadata) for more information.

### Operational templates

If you are building an EHR implementation, operational templates are likely the most useful form of archetypes to work with. An operational template is generated from an archetype or template. In an archetype, structures can be reused in several places and other archetypes can be embedded. The operational template replaces these references with a copy of the actual structure, so your tools do not need to resolve them. See [the openEHR OPT2 specification](https://specifications.openehr.org/releases/AM/latest/OPT2.html) for more information.

Note that ADL 2 operational templates are fundamentally different from the ADL 1.4 OET/OPT format. What used to be done with OET/OPT is now done with ADL 2 templates, in combination with operational template creation. See [the openEHR specification on templates](https://specifications.openehr.org/releases/AM/latest/ADL2.html#_templates) on how to work with them.

To create an operational template:

```java
Flattener flattener = new Flattener(repository, BuiltinReferenceModels.getMetaModelProvider()).createOperationalTemplate(true);
OperationalTemplate template = (OperationalTemplate) flattener.flatten(sourceArchetype);
```

Pass the original, differential archetype, not a flattened version.

- A flattener can be used only once. To flatten another archetype, create a new `Flattener`.
- To keep only some languages in the terminology, call `flattener.keepLanguages("en", "nl")` before flattening. To also remove the other languages from the archetype metadata, call `flattener.removeLanguagesFromMetadata(true)`.
- Without the `createOperationalTemplate(true)` call, the flattener creates a flattened archetype instead of an operational template.

### Terminology

You can use `archetype.getTerminology()` to get the texts and descriptions of nodes in any language. Archie has some convenience methods to make this easier. You can set the language to use for the current thread, and get terms directly from the archetype constraints:

```java
ArchieLanguageConfiguration.setThreadLocalDescriptiongAndMeaningLanguage("nl");

CObject cobject = archetype.getDefinition().getAttribute("context").getChild("id1");
ArchetypeTerm term = cobject.getTerm();
logger.info("and the archetype term text in Dutch is: " + term.getText());
```

This works both with the terminology of a differential archetype and with the component terminologies of operational templates. Use `ArchieLanguageConfiguration.setDefaultMeaningAndDescriptionLanguage(...)` to change the default language for all threads.

You can also specify the language yourself:

```java
CObject cobject = archetype.getDefinition().getAttribute("context").getChild("id1");
ArchetypeTerm term = archetype.getTerm(cobject, "en");
logger.info("and the archetype term text in English is: " + term.getText());
```

Or access the terminology directly:

```java
archetype.getTerminology().getValueSets();
operationalTemplate.getComponentTerminologies();
```

For terminology constraints with locally defined values:

```java
CTerminologyCode cTerminologyCode = archetype.itemAtPath("/somePath...");
List<TerminologyCodeWithArchetypeTerm> terms = cTerminologyCode.getTerms();

// or for a single code:
ArchetypeTerm term = archetype.getTerm(cTerminologyCode, "at15", "en");
```

### Diffing archetypes

Diffing is the inverse of flattening. It is useful when writing a tool to edit archetypes: users can edit the flat form, which is much easier to understand, after which you store the output of the differentiator as the differential form.

```java
Archetype flatChild, flatParent; // see above for how to parse and flatten

Differentiator differentiator = new Differentiator(BuiltinReferenceModels.getMetaModelProvider());
Archetype diffed = differentiator.differentiate(flatChild, flatParent);
```

Use flattened archetypes for both the parent and the specialized archetype. Do not use operational templates.

The differentiator diffs the definition and the terminology of the archetype. It:

- adds sibling order markers to preserve the ordering of C_OBJECTs in the specialized archetype. It only adds them where necessary, and adds as few as possible
- removes default or unspecialized cardinality, occurrences and existence
- removes unspecialized C_OBJECTs, C_ATTRIBUTEs and tuples
- generates differential paths where possible
- generates a diff of the terminology, including term definitions, term bindings and value sets
- removes translations that exist in the parent archetype, but not in the specialized archetype
- removes terminology extracts

It returns a new archetype. The input archetypes are not changed.

The differentiator does not diff template overlays when given a template. You can however diff a flattened template overlay with its flat parent, and replace the template overlay in the template with the result yourself. The rules section is not diffed either.

### Walking the archetype tree

`getAttributes()` is defined on `CObject`, so walking the archetype tree takes just a few lines of code:

```java
public void walk(CObject cobject) {
    for (CAttribute attribute : cobject.getAttributes()) {
        for (CObject child : attribute.getChildren()) {
            walk(child);
        }
    }
}
```

## Serialization

### ADL

Archetypes can be serialized to ADL, thanks to the serializer written by @markopi64 from Marand Labs:

```java
String serialized = ADLArchetypeSerializer.serialize(archetype);
```

This works for all kinds of archetypes, including operational templates.

### JSON

Both archetypes and reference model objects can be serialized to and parsed from JSON using Jackson. `JacksonUtil` provides a fully configured `ObjectMapper`:

```java
String json = JacksonUtil.getObjectMapper().writeValueAsString(archetype);
Archetype parsedArchetype = JacksonUtil.getObjectMapper().readValue(json, Archetype.class);
```

The JSON output contains some extra fields that make it easier to use in JavaScript, such as paths and the texts of nodes in the language of your choice. These fields are ignored when parsing.

### XML

XML serialization uses JAXB. The XML output for the reference model conforms to the official openEHR RM XSD. There is no official XSD for the AOM 2 yet, so the AOM XML output conforms to the development AOM 2.0 format, which may still change.

```java
Marshaller marshaller = JAXBUtil.getArchieJAXBContext().createMarshaller();
StringWriter writer = new StringWriter();
marshaller.marshal(archetype, writer);
String xml = writer.toString();

Unmarshaller unmarshaller = JAXBUtil.getArchieJAXBContext().createUnmarshaller();
Archetype parsedArchetype = (Archetype) unmarshaller.unmarshal(new StringReader(xml));
```

### Jackson 3

Parsing, ADL serialization and JSON can also be used with Jackson 3:

```java
ADLParser3 parser = new ADLParser3();
Archetype archetype = parser.parse(adlFile);

String serialized = ADLArchetypeSerializer.serializeWithJackson3(archetype, null, new ArchieRMObjectMapperProvider());

String json = JacksonUtil3.getObjectMapper().writeValueAsString(archetype);
Archetype parsedArchetype = JacksonUtil3.getObjectMapper().readValue(json, Archetype.class);
```

The ODIN classes have Jackson 3 variants as well, such as `OdinObjectParser3` and `ODINMapper3`.

### ODIN

ODIN is a JSON/YAML-like notation used in ADL for metadata, terminologies and annotations. See https://github.com/openehr/odin for more information. Archie can map ODIN directly to Java objects using Jackson:

```java
YourType type = OdinObjectParser.convert(odinText, YourType.class);
```

This works by first converting ODIN to JSON, then binding that JSON to objects with Jackson. Most ODIN features are supported, except:

- intervals of anything other than integers
- object references

To serialize your own objects to ODIN, use the `ODINMapper`. Unlike most Jackson object mappers, it can only serialize ODIN, not parse it:

```java
ODINMapper mapper = new ODINMapper();
String result = mapper.writeValueAsString(yourObject);
```

Like any other Jackson `ObjectMapper`, the mapping is configurable, for example with custom type mappings.

## Reference model

Archie contains an implementation of the openEHR reference model version 1.1.0, without the task planning part, plus tools to work with reference model objects.

### Creating reference model objects

The `ExampleJsonInstanceGenerator` generates example JSON instances from an operational template. They can be parsed and used as examples, or as a starting point for new reference model objects:

```java
ExampleJsonInstanceGenerator generator = new ExampleJsonInstanceGenerator(BuiltinReferenceModels.getMetaModelProvider(), "en");
Map<String, Object> example = generator.generate(operationalTemplate);
String json = JacksonUtil.getObjectMapper().writeValueAsString(example);
```

To build reference model objects yourself, the `RMObjectCreator` creates an empty reference model object for a given constraint. If the constraint uses an abstract class, it picks a non-abstract descendant class:

```java
RMObjectCreator creator = new RMObjectCreator(ArchieRMInfoLookup.getInstance());
RMObject rmObject = creator.create(cComplexObject);
```

You can then set attribute values directly on the created objects, or with the `ModelInfoLookup`.

`ArchieRMInfoLookup.getInstance()` provides the metadata about the openEHR reference model implementation. See [Using a different reference model implementation](#using-a-different-reference-model-implementation) to use your own.

### Parsing reference model JSON

Reference model JSON is parsed the same way as archetype JSON:

```java
RMObject rmObject = JacksonUtil.getObjectMapper().readValue(json, RMObject.class);
```

or if you know which class to expect:

```java
Composition composition = JacksonUtil.getObjectMapper().readValue(compositionJson, Composition.class);
```

### Reference model path queries

```java
List<Object> items = rmObject.itemsAtPath("/data[id2]/items");
```

To get the unique path of every returned object as well, use the lower level `RMPathQuery`:

```java
List<RMObjectWithPath> itemsWithUniquePaths = new RMPathQuery("/data[id2]/items").findList(ArchieRMInfoLookup.getInstance(), rmObject);
```

### Validating reference model objects against an archetype

The `RMObjectValidator` validates reference model objects against an operational template. It validates:

- cardinality
- occurrences
- existence
- data types
- primitive object constraints
- tuples

Cardinality and existence are validated against both the archetype and the reference model.

```java
RMObjectValidator validator = new RMObjectValidator(
        ArchieRMInfoLookup.getInstance(), // or a different ModelInfoLookup for other reference models
        operationalTemplateProvider,
        new ValidationConfiguration.Builder().build());
List<RMObjectValidationMessage> validationMessages = validator.validate(operationalTemplate, rmObject);
```

The validator only works with operational templates, not with differential or flattened archetypes. See [Operational templates](#operational-templates) on how to create them. The `OperationalTemplateProvider` is used to get the operational templates of archetypes that are used in archetype slots. `InMemoryFullArchetypeRepository` implements this interface. It only returns operational templates that were stored in it with `setOperationalTemplate(...)`.

`ValidationConfiguration.Builder` has options to also validate the reference model invariants, and to fail on unknown terminology ids.

### Intervals and primitive object constraints

`Interval` implements the `has(value)` method:

```java
new Interval<>(2, 4).has(3); // returns true
Interval.upperUnbounded(2, true).has(1); // returns false
```

To check whether a value conforms to a C_PRIMITIVE_OBJECT constraint, use the `RMObjectValidator`, or the
`ValidationHelper` it is built on:

```java
CString cString = new CString();
cString.addConstraint("test");
cString.addConstraint("/more te+st/");

ValidationHelper helper = new ValidationHelper(ArchieRMInfoLookup.getInstance(), new ValidationConfiguration.Builder().build());
helper.isValidValue(cString, "test"); // returns true
helper.isValidValue(cString, "more teeeeest"); // returns true - regexp matching
helper.isValidValue(cString, "mooooore test"); // returns false
```

ISO 8601 date constraint patterns are not yet supported.

## Converting ADL 1.4 archetypes to ADL 2

Archie can parse ADL 1.4 archetypes and convert them to ADL 2:

```java
MetaModelProvider metaModelProvider = BuiltinReferenceModels.getMetaModelProvider();
ADL14ConversionConfiguration conversionConfiguration = new ADL14ConversionConfiguration();
ADL14Converter converter = new ADL14Converter(metaModelProvider, conversionConfiguration);
ADL14Parser parser = new ADL14Parser(metaModelProvider);

List<Archetype> archetypes = new ArrayList<>();
for (String file : fileNames) {
    try (InputStream stream = new FileInputStream(file)) {
        archetypes.add(parser.parse(stream, conversionConfiguration));
    } catch (ADLParseException e) {
        // handle the parse error
    }
}

ADL2ConversionResultList resultList = converter.convert(archetypes);
for (ADL2ConversionResult adl2ConversionResult : resultList.getConversionResults()) {
    if (adl2ConversionResult.getException() == null) {
        // the ADL 2 result. Warnings are available in adl2ConversionResult.getLog()
        Archetype convertedArchetype = adl2ConversionResult.getArchetype();
    }
}
```

The converted archetypes are in differential ADL 2 form. Things to keep in mind:

- Run the converted archetypes through the archetype validator, especially specialized archetypes. ADL 1.4 tooling often has limited validation for specialized archetypes, so they often contain errors.
- To convert a specialized archetype, pass both the specialized archetype and its parent to the converter in the same call. Otherwise the `ADL2ConversionResult` will contain an exception.
- ADL 2 requires node ids at some places where they are optional in ADL 1.4, so the converter generates new id codes. How to do this has not been standardized, so other tools may generate different ADL 2 archetypes from the same input.

### Storing the conversion log

To use the converter in a modeling tool, where you edit in ADL 1.4 but want to output both ADL 1.4 and ADL 2, the converter must generate the same node ids after every edit. To do so, pass the conversion log of the previous conversion to the next one:

```java
ADL2ConversionResultList resultList = converter.convert(archetypes, previousResultList.getConversionLog());
```

The conversion log can be serialized with Jackson, so it can be stored alongside the ADL 1.4 archetypes.

### Conversion configuration

The `ADL14ConversionConfiguration` specifies how term codes as used in ADL 1.4 are mapped to the term URIs used in ADL 2. See [`ConversionConfigForTest.java`](tools/src/test/java/com/nedap/archie/adl14/ConversionConfigForTest.java) for an example of how this works and how to serialize it to a file, and [`configuration.json`](tools/src/test/resources/com/nedap/archie/adl14/configuration.json) for a simple serialized configuration with sane defaults for SNOMED CT, LOINC and openEHR URIs.

If you leave the configuration empty, the converter falls back to a default URI conversion.

## Advanced usage

### Reference model metadata

Archetype tools need metadata about the reference model to work. This can be the openEHR reference model, but also another model. For most users, `BuiltinReferenceModels.getMetaModelProvider()` is enough. This section is for when you want to add your own reference models or metadata.

Archie supports two types of metadata:

- **Reflection based metadata**, derived from a Java implementation of a reference model, in the form of a `ModelInfoLookup`. Two are included: `ArchieRMInfoLookup` for the openEHR reference model, and `TestRMInfoLookup` for the openEHR test models in the `test-rm` module. The built-in metadata only contains the lookups for the modules you depend on. If you depend on `archie-all`, the openEHR reference model is included.
- **BMM metadata**, which is not based on an implementation, but on a file in the BMM format defined by openEHR. See [the BMM specification](https://specifications.openehr.org/releases/LANG/latest/bmm.html).

A `MetaModel` combines both types of metadata, and a `MetaModelProvider` provides the `MetaModel` for a given archetype or reference model version. If a BMM model is available for an archetype, it is used where possible.

To use your own BMM files, parse them, then load the AOM profiles:

```java
BmmRepository bmmRepository = new BmmRepository();
for (String fileName : bmmFiles) {
    try (InputStream stream = new FileInputStream(fileName)) {
        bmmRepository.addPersistentSchema(BmmOdinParser.convert(stream));
    }
}
BmmSchemaConverter converter = new BmmSchemaConverter(bmmRepository);
converter.validateAndConvertRepository();

AomProfiles aomProfiles = new AomProfiles();
for (String fileName : aomProfileFiles) {
    try (InputStream stream = new FileInputStream(fileName)) {
        aomProfiles.add(stream);
    }
}

MetaModelProvider metaModelProvider = new SimpleMetaModelProvider(
        new ReferenceModels(ArchieRMInfoLookup.getInstance()), bmmRepository, aomProfiles);
```

This creates a `MetaModelProvider` with the Archie reference model implementation, the BMM models and the AOM profiles. The flattener and archetype validator use the BMM models and AOM profiles. Tools that work on reference model objects use the reflection based metadata.

After validating and converting, the `BmmRepository` gives access to the P_BMM schemas, the BMM models and all validation messages through the `BmmValidationResult` class. See the Javadoc for more information.

### Validating a single archetype

The [archetype repository](#archetype-repositories-and-validation) validates all archetypes at once. To validate a single archetype without any parent or included archetypes, use the `ArchetypeValidator` directly:

```java
ValidationResult validationResult = new ArchetypeValidator(BuiltinReferenceModels.getMetaModelProvider()).validate(archetype);
```

The result contains the validation messages, the validation results of any template overlays and the flattened archetype.

### BMM and P_BMM

Archie implements BMM version 2.2 and P_BMM version 2.3.0. See [Reference model metadata](#reference-model-metadata) on how to parse P_BMM and convert it to BMM. There are some differences with the specification, to simplify the implementation:

- The P_BMM implementation only contains the persisted fields, and does not keep any state about the conversion to BMM.
- BMM_SCHEMA and REFERENCE_MODEL_ACCESS are not used. Use `BmmValidationResult` instead of BMM_SCHEMA, and `BmmRepository` instead of REFERENCE_MODEL_ACCESS.
- BMM_SCHEMA_DESCRIPTOR and P_BMM_SCHEMA_DESCRIPTOR are not used, and have no direct replacement.

P_BMM is bound to Jackson, so it can be serialized to ODIN:

```java
String odin = new BmmOdinSerializer().serialize(pBmmSchema);
```

It can also be serialized to and parsed from JSON or YAML. Use `BmmJacksonUtil.getObjectMapper()` for JSON.

### Default constraints from the reference model

An archetype constrains instances of the reference model, but the reference model also has default constraints. For example, the `data` attribute of an OBSERVATION is single valued, not a list or set. This affects the default cardinality and existence, and methods such as `isMultiple()` and `isSingle()` on C_ATTRIBUTE. To set these values when parsing, pass a `MetaModelProvider` to the parser:

```java
Archetype archetype = new ADLParser(BuiltinReferenceModels.getMetaModelProvider()).parse(adlFile);
```

This is generally not needed when you use an archetype repository.

### Using a different reference model implementation

Archie uses its own openEHR reference model implementation by default, but it can work with other implementations. To do so, implement a `ModelInfoLookup` for your reference model, usually by extending `ReflectionModelInfoLookup` with your own `ModelNamingStrategy`. See `ArchieRMInfoLookup` and `TestRMInfoLookup` for examples. Then register it in a `ReferenceModels` instance and use that to create a `SimpleMetaModelProvider`.

## Experimental features

The following features can be used, but their API is likely to change in future versions.

### Rule evaluation

Archie has a basic implementation of the evaluation of rules in archetypes, in the `RuleEvaluation` class. The result is a list of assertions, each noting:

- whether it evaluated to true or false
- whether it can be fixed automatically, or the user needs to take a step
- what must be done to fix the rule automatically, by setting paths to values and paths that must exist or not exist
- which fields were used to evaluate the result, so errors can be shown

You can link this to a user interface that sets paths to values, hides or shows fields and displays validation messages. This makes it easy to implement things like score calculations and conditional fields. For example, score calculations:

```
/path/to[id12]/score_result = /path/to[id12]/field_one + /path/to[id12]/field_two
```

Conditionally hiding fields:

```
/path/to[id12]/score_result > 3 implies exists /path/to/hidden/field
```

Or validations that the user must fix:

```
total_score_must_be_high: /path/to[id12]/score_result + /some_other_score > 24
```

Supported are comparison and arithmetic operators, path retrieval, `exists` and `not exists`, `implies`, variable declaration and use, and `for_all`. Integer, string and boolean literals are supported. String literals can only be used with the `=` and `!=` operators. This means you can set fields to string values, including the code strings of DV_CODED_TEXT and DV_ORDINAL fields.

Rules are very similar to XPath expressions. The specification does not define how to handle multiplicities in paths, so where these occur outside of a `for_all` rule, the W3C XPath 1 specification is used.

### Full XPath support on the reference model

The `RMQueryContext` provides full XPath 1 support on reference model objects. APath shorthand notations like `/items[id2]` are converted to the corresponding XPath. It uses the JAXB `Binder` to get a DOM to run XPath on. You can choose your own JAXB implementation with the usual mechanisms, although only the default implementation has been tested.

## Building from source

To build Archie, check out the source and run:

```sh
./gradlew build
```

To install it in your local Maven repository, for use in other Gradle or Maven projects:

```sh
./gradlew publishToMavenLocal
```
